# Snake3D

Snake3D is a browser-based 3D interpretation of the classic Snake game. It is built
with React, TypeScript, Vite, React Three Fiber, and Three.js.

The current development goal is to turn the existing pet project into a stable,
mobile-ready commercial MVP through specification-driven development, automated
verification, and small reviewable changes.

## Current status

The game already contains a 3D scene, snake movement, food, obstacles, levels, scores,
lives, bonuses, timers, keyboard controls, menu/pause UI, and a Playwright random-play
stability test.

The project is still pre-release. Important work remains around deterministic tests,
restart/state reset, player onboarding, mobile UX, performance, accessibility,
production monitoring, and release validation.

See [`docs/roadmap.md`](docs/roadmap.md) for priorities and
[`docs/architecture-map.md`](docs/architecture-map.md) for the current architecture.

## Installation

```bash
git clone <repository-url>
cd snake3D && npm ci
npx playwright install chromium
```

If `npm ci` cannot be used because the lockfile is missing or intentionally changed,
use `npm install`, then review and commit the resulting lockfile deliberately.

## Automated tests

```bash
npm run test:e2e
```

The current Playwright suite launches the Vite development server and performs a long
randomized gameplay stability check. It is useful for detecting crashes, hangs, page
errors, and console failures, but it does not replace deterministic unit and scenario
tests.

## Current verification gate

Before considering a code change ready for review, run the deterministic aggregate gate:

```bash
npm run verify
```

Before considering code work complete, also run the browser stability gate:

```bash
npm run test:e2e
```

`npm run verify` runs type checking, linting, deterministic unit tests, and the
production build. `npm run test:e2e` remains the Playwright browser stability check.

| Command | Purpose | Likely failure owner |
|---|---|---|
| `npm run typecheck` | Checks strict TypeScript types without emitting files. | Contributor who changed TypeScript contracts or imports. |
| `npm run lint` | Checks focused source and test lint rules. | Contributor who changed source, tests, or lint configuration. |
| `npm run test:unit` | Runs deterministic Vitest checks under `tests/unit`. | Contributor who changed isolated rules, utilities, or unit-test setup. |
| `npm run build` | Typechecks and creates the production Vite bundle. | Contributor who changed app code, build config, or dependencies. |
| `npm run verify` | Runs `typecheck`, `lint`, `test:unit`, and `build` in order, stopping at the first failing area. | Contributor preparing the change for review. |
| `npm run test:e2e` | Runs the Playwright browser stability suite. | Contributor who changed gameplay, browser behavior, or e2e setup. |

Pull requests run `npm ci` and `npm run verify` through the `Quality Gates` GitHub
Actions workflow. Maintainers should treat a failing workflow as not ready for merge
until the failing quality area is fixed. Browser stability coverage is still required
before code work is complete, even though it is kept separate from the deterministic PR
workflow.

## Project structure

```text
src/
├── animations/      # Snake and food animation logic
├── assets/          # 3D models and model-related code
├── commands/        # Browser and utility commands
├── components/      # React and React Three Fiber components
├── config/          # Static application and scene configuration
├── engine/          # Gameplay state, rules, events, levels, scoring, timers
├── hooks/           # React hooks
├── store/           # Zustand UI stores
├── styles/          # Global/component CSS
└── types/           # Shared TypeScript types

tests/e2e/           # Playwright end-to-end tests
docs/                # Architecture, roadmap, and SDD feature artifacts
```

## Architecture

The current engine uses module-level mutable state with getter/setter functions, while
React Three Fiber frame callbacks advance gameplay and update rendered objects. Read
[`docs/architecture-map.md`](docs/architecture-map.md) before making structural changes.

That document is generated by the SDD `survey` stage. Refresh it after significant
architecture changes rather than editing it casually.

## Agent-assisted development

Repository-specific instructions for Codex and other coding agents are in
[`AGENTS.md`](AGENTS.md).

For feature work:

1. Choose an approved item from `docs/roadmap.md`.
2. Create or use `docs/features/<slug>/`.
3. Run the SDD stages: specify, design, tasks, implement, review, ship.
4. During implementation, use small RED → GREEN → REFACTOR → GATE → COMMIT loops.
5. Review gameplay and visual changes manually before merge or release.

## Controls

Keyboard controls exist in the current build, but the final player-facing control list
must be verified against the implementation before public release. Mobile controls are
part of the commercial MVP roadmap.

## Product direction

The first commercial milestone is not accounts, payments, or multiplayer. It is a
polished playable loop:

```text
open game → understand controls → play → receive clear feedback → lose/finish →
see result → restart → want to play again
```

After the MVP is published, product decisions should be driven by player testing,
retention, performance data, and feedback rather than feature volume alone.
